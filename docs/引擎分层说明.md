# 引擎分层说明

> 这份文档解释**为什么引擎里搜不到领域词**，以及**换一个领域要动哪里**。

---

## 一、两层，各管什么

| | 通用层 `engine/engine.py` | 领域层 `engine/color_rules.py` |
|---|---|---|
| 管什么 | 属性档位、配对判定、状态、深浅调制、标注解析 | 哪些符号参与对立；每一对的激烈程度、是否改属性、含义怎么来 |
| 换领域时 | **一行都不改** | **整个替换** |
| 语言 | 只有"元素 / 属性 / 配对"这类抽象词 | 全是具体符号名 |

**验收标准一句话**：

> **引擎源码里搜不到任何具体符号名（牌名 / 花色名 / 颜色名）。**

⚠️ **注意这个声称的边界**：它**不等于**"引擎里没有任何领域概念"。
层名称（背景 / 中景 / 前景 / 空间层）与 `card_id` **仍然是引擎里的领域遗留**——见文末第六节。

---

## 二、两层的接口约定

`engine/engine.py` 在**文件末尾**导入领域层：

```python
# engine/engine.py 末尾
from color_rules import (
    OPPOSITION_RECIPE,
    intensity_of,
    is_opposition_pair,
    resolve_opposition,
)

# 层结构也归领域层（领域不声明时用引擎的默认四层）
try:
    from color_rules import LAYERS as _DOMAIN_LAYERS
except ImportError:
    _DOMAIN_LAYERS = None
if _DOMAIN_LAYERS:
    LAYERS = tuple(_DOMAIN_LAYERS)
```

**这就是全部契约 —— 5 个名字。** 领域层只要提供它们，引擎就能工作。

### 为什么放在文件末尾

这是**故意**的，不是随手写的：

```
color_rules.py 里要 `from engine import Attribute`
   ↓
如果 engine.py 在【开头】就导入 color_rules，
那时 Attribute 还没定义 → 循环导入
   ↓
放到【最后】：等上面的定义全部完成再导入，问题消失
```

### 四个名字的语义

| 名字 | 作用 |
|---|---|
| `LAYERS` | **本领域有哪几层、各叫什么**（元组）。引擎读它；不给就用默认四层 |
| `OPPOSITION_RECIPE` | 配方表：`frozenset({符号A, 符号B}) → 配方 dict` |
| `is_opposition_pair(a, b)` | **只定位**：这一对算不算合法对立 |
| `intensity_of(a, b)` | 激烈程度；不成对立返回 `None` |
| `resolve_opposition(a, b, meanings_a, meanings_b)` | **推导**：返回 `{intensity, attr_a, attr_b, meanings_a, meanings_b}`；不成对立返回 `None` |

配方 dict 的字段：

| 字段 | 含义 |
|---|---|
| `intensity` | 激烈程度 |
| `change_attr` | 是否改属性 |
| `attr_self` / `attr_other` | 改属性时，本色 / 对面变成什么 |
| `meanings` | 手写调制含义；`None` 表示用「非X」生成 |

**注意**：「定位」与「推导」是两个函数。`is_opposition_pair` 只回答"算不算"，不改任何东西；`resolve_opposition` 才产出结果。这个拆分是为了让"找对子"的过程可以独立测试。

## 三、哪些规则该放哪一层

这是本设计里最值得说的一条判断：

| 规则 | 放哪层 | 为什么 |
|---|---|---|
| **深浅**（进一档 / 退一档） | **引擎层** | 它**对任何符号都成立、没有特例** → 属于通用规律 |
| **对立**（哪两对合法、怎么改） | **领域层** | 它**是领域特定的**（哪个领域参与对立、有几对、什么激烈程度，都是领域知识） |

> **判断标准：一条规则如果对所有领域都成立，就放引擎层；只要它依赖"具体是哪些符号"，就放领域层。**

这条标准可以直接套用到新领域上。

---

## 四、换一个领域，要做什么

1. **写一个新的领域层文件**，提供第二节那四个名字
2. `engine/engine.py` **一个字都不改**
3. 换掉字典（字典回答两个问题：哪些名字算这个类别；某个名字的属性与含义）
4. 跑 `demo/demo_daily.py` 验证接口通不通

本仓库附带的 `engine/color_rules.py` 就是**用第 1 步做出来的示例**——它装的是【光 / 影 · 暖 / 冷】，不是颜色。**引擎不知道这两者的区别，因为它只调用接口。**

---

## 五、为什么不做程度量化

引擎的判定函数 `judge(a, b)` **只返回 `(状态, 偏向)`，不返回强度**。

三档基础表只有 6 行；`极` / `衰` 折回基础三档后再查表（`极阳 + 阳` → 折回 `阳 + 阳` → 重叠）。

> **属性档位的变化只服务于含义，不参与计量。**

这条是刻意的：一旦把属性换算成数字，就会开始算"强度"，而强度会让"留白"消失——**三态里的「交汇」是主动留出来的呼吸空间，不是"没法判断"**。

---

## 六、残留与边界（如实标注）

**曾经的问题**：层结构（背景 / 中景 / 前景 / 空间层）写死在引擎里，是**塔罗的壳**。换领域时每个新领域都得迁就它。

**✅ 已解决**：层结构现在由**领域层声明**（`LAYERS`），引擎从接口读；领域不声明时用引擎的默认四层。**验证方式**：本仓库的玩具领域层声明了 `("表层", "里层", "底层")`，而 `demo/demo_daily.py` 会同时打印"领域声明的层"和"引擎实际使用的层"——两者一致。

**⚠️ 仍存在的（只剩命名）**：

| 残留 | 位置 | 影响 |
|---|---|---|
| `card_id` / `source_id` | `engine.py` 参数名 | **纯命名**：参数名仍带"牌"的语境，不影响行为 |
| 注释里的"牌"字 | 多处 | 文档遗留 |

**为什么要把这些写出来**：一个技术读者会自己 grep。**把"还差什么"先写出来，比声称"已完成"可信得多。**
